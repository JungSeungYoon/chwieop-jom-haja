# [동아리 과제] 공대생 포트폴리오 서비스 ‘취업좀하자’ 기획과 개발 기록

> 작성일: 2026년 10월 5일 · 현재 상태: 기획 초안
>
> 이 글은 서비스 기획부터 구현, 오류 해결, 검증, 배포까지 하나의 글에 누적하는 개발 기록이다. 상단에는 계획서를, 하단에는 날짜별 진행 과정을 정리한다. 아래 내용은 구현 완료 보고가 아니라 목표와 계획이다.

## 1. 어떤 서비스를 만들 것인가

서비스 이름은 **취업좀하자**다. 개발·통신·보안을 비롯한 공학 분야의 학생들이 자신이 수행한 프로젝트와 공부 내용을 올리고, 이를 개인 포트폴리오로 보여줄 수 있는 웹 서비스다.

한 사람의 개인 홈페이지만 제작하는 것이 아니라, 여러 사용자가 가입하여 각자의 포트폴리오와 아카이브를 만드는 것이 목표다. 사용자는 프로젝트, 공부 기록, 기타 글을 직접 작성하고 자신의 공개 페이지에서 소개할 수 있다.

## 2. 기획 배경과 해결하려는 문제

현재 대화에서 확인한 출발점은 ‘공대생의 프로젝트와 학습 과정을 잘 드러내는 포트폴리오 공간을 만들고 싶다’는 것이다. 결과물뿐 아니라 맡은 역할, 설계 선택, 실험, 문제 해결 과정도 기록할 수 있도록 구성한다.

**작성자의 실제 경험과 불편함은 확인 후 이 문단에 추가한다.** 기존 서비스에 대한 불만이나 사용자 조사를 실시했다는 내용은 임의로 작성하지 않는다.

## 3. 대상 사용자와 서비스의 특색

주요 대상은 프로젝트·실습·학습 경험을 정리하고 싶은 공대생이다. 특히 개발, 통신, 보안처럼 코드와 실험 결과, 기술적 설명이 중요한 분야를 고려한다.

차별점은 다음 세 가지로 잡았다.

1. **유형별 작성 안내**: 무엇을 써야 하는지 항목으로 안내하되, 본문은 자유롭게 작성한다.
2. **학습과 결과물의 연결**: 공부 기록을 프로젝트와 연결하여 ‘무엇을 배워 어디에 적용했는지’를 보여준다.
3. **축적과 공개를 함께 지원**: 비공개로 공부 메모를 쌓다가 정리한 뒤 공개하고, 대표 프로젝트를 핀으로 강조한다.

기존 GitHub·티스토리·노션의 사용을 중단하도록 요구하기보다, 원문 링크와 필요한 가져오기 기능을 통해 기존 기록과 연결하는 방향을 검토한다.

## 4. 지금까지 정한 기능

| 기능 | 계획한 동작 |
|---|---|
| 회원별 포트폴리오 | 여러 사용자가 자신의 프로필과 공개 기록을 모아 보여준다. 가입·로그인 방식은 이후 결정한다. |
| 글 유형 선택 | 새 글에서 프로젝트 / 공부 기록 / 기타를 선택한다. |
| 프로젝트 작성 | 목표, 내 역할, 사용 기술·장비, 문제와 해결, 결과를 안내하고 자유 본문을 제공한다. |
| 공부 기록 작성 | 학습 주제, 참고 자료, 이해한 내용, 실습, 남은 질문을 안내하고 자유 본문을 제공한다. |
| 기타 작성 | 제목·태그와 자유 본문으로 회고·활동 후기 등을 작성한다. |
| 블로그형 편집기 | 버튼으로 본문을 편집한다. 사진·코드 블록·수식 등 공학 기록에 필요한 표현을 지원하는 방향이다. 세부 편집 기능은 화면 설계 때 확정한다. |
| 공개 범위 | 전체 공개 / 나만 보기를 선택하고 작성 후 변경할 수 있다. 비공개 기록은 본인만 접근한다. |
| 대표 프로젝트 핀 | 자신의 공개 프로젝트를 포트폴리오 상단에 고정한다. 비공개 전환 시 공개 화면에서 제외한다. 개수와 정렬 방식은 미정이다. |
| 보관함 | 다른 사람의 공개 기록을 저장·해제한다. 새로고침과 재로그인 후 유지한다. 원글이 비공개가 되면 내용을 노출하지 않는다. |
| 전체 검색 | 모든 공개 기록을 검색하고 글 유형·기술 태그로 범위를 좁힌다. |
| 개인 검색 | 개인 포트폴리오의 공개 기록을 검색한다. 본인의 관리 화면에서는 비공개 기록도 검색한다. |
| 기록 연결 | 자신의 프로젝트와 공부 기록을 연결하고 양쪽에서 관련 기록을 확인한다. 방문자에게 비공개 기록은 보여주지 않는다. |
| 반응형·상태 처리 | 모바일과 PC를 지원하고 로딩, 결과 없음, 요청 실패를 구분한다. 저장 실패 시 입력을 유지한다. |

댓글·팔로우·좋아요는 첫 버전에서 제외하고 후속 기능으로 미룬다. 이름이 ‘취업좀하자’라고 해서 채용 공고·지원·기업 매칭 기능까지 포함하는 것은 아니다. 현재 목표는 자신의 기술 경험을 정리하고 보여주는 것이다.

## 5. 외부 서비스 연동은 어디까지 할 것인가

| 서비스 | 가능한 방향 | 현재 결정 상태 |
|---|---|---|
| GitHub | 공개 저장소의 설명·README 등을 가져와 프로젝트 초안에 활용, 원문 저장소 링크 표시 | 첫 연동 기능으로 제안했으며 범위는 아직 확정하지 않았다. 비공개 저장소와 자동 동기화는 별도 검토한다. |
| Notion | 원문 링크, 사용자가 허용한 페이지 내용 가져오기·내보내기 | 도입 단계와 범위 미정. 여러 사용자의 페이지 접근에는 사용자별 권한 연결이 필요하다. |
| Tistory | 원문 링크, 붙여넣기용 글 내보내기 | 공식 Open API가 종료되어 공식 API 자동 발행은 사용할 수 없다. |

이 서비스의 외부 연동 기능과, 작성자 본인의 과제 개발 기록을 티스토리에 게시하는 작업은 별개다. 후자는 Codex가 글 초안·설명·실제 화면 캡처를 준비하고 작성자가 검토하는 방식으로 시작한다. 브라우저 업로드 자동화는 실제 로그인·에디터 환경을 확인한 뒤 가능 범위를 정한다.

## 6. 예산과 기술 구성

추가 예산은 **0원**이다. 이미 이용 중인 ChatGPT Plus 구독에서 Codex GPT-6.1 Sol Medium을 개발 보조로 사용한다. 웹 서비스 운영에 유료 OpenAI API나 별도 AI 호출을 넣는 계획은 없다.

사용자가 제안한 배포 후보는 **Vercel**, DB 후보는 **Supabase**다. ‘슈퍼DB’가 Supabase를 뜻하는지는 확인 중이다.

| 항목 | 후보와 판단 |
|---|---|
| 웹 호스팅 | Vercel Hobby. 개인·비상업적 용도 조건과 사용량 제한을 확인하여 과제용 배포에 사용한다. |
| DB | Supabase Free의 PostgreSQL. 사용자·기록·핀·보관·연결 관계를 저장한다. |
| 로그인 | Supabase Auth 활용을 검토한다. GitHub 로그인 등 실제 방식은 아직 정하지 않았다. |
| 사진 저장 | Supabase Storage 활용을 검토한다. 이미지 크기·개수 제한을 정할 필요가 있다. |
| 프레임워크 | 미정. Vercel과 잘 맞는 Next.js + TypeScript를 후보로 검토하되 환경 구성 전에 결정한다. |
| 도메인 | 비용이 없는 기본 배포 주소를 우선 사용한다. 별도 도메인은 구매하지 않는다. |

2026년 10월 5일 공식 안내 기준, Supabase Free에는 DB 500MB, 파일 저장 1GB가 포함되어 있고 비활성 프로젝트는 약 1주 후 일시 중지 대상이 된다. 무료 플랜은 자동 백업도 포함하지 않는다. 데이터와 파일의 별도 백업 계획이 필요하다. 무료라고 해서 용량·트래픽·운영 기간이 무제한인 것은 아니다.

Vercel Hobby는 비상업적 개인 프로젝트 조건을 확인해야 한다. 첫 배포는 비상업적 과제로 운영하고, 수익화나 운영 규모 변경 시 플랜 적합성을 다시 검토한다. 유료 전환·추가 크레딧·유료 부가 기능을 자동으로 활성화하지 않는다.

| 요구사항 | 대응 계획 |

| 로딩·결과 없음·요청 실패 | 각 상태별 화면과 재시도, 저장 실패 시 입력 보존 |
| 즐겨찾기 또는 보관 | 사용자별 보관함 |

| README와 실행 방법 | 환경 변수, 설치·실행·검증·배포 절차를 구현 과정에서 작성 |
| Git 커밋 5개 이상 | 실제 단계별 작업을 의미 있는 커밋으로 기록 |
| 기능명세서·API 명세서 | 기획 확정 후 별도 문서로 작성하고 구현과 일치하도록 수정 |
| ERD | 여러 사용자의 권한과 기록 관계가 있으므로 작성 |
| GitHub 제출 | 코드·문서·커밋 기록·배포 주소를 정리 |
| 블로그 기록 | 파일별 역할, 코드 흐름, API 요청→화면 출력, AI 활용·수정·검증, 오류와 해결을 하나의 글에 누적 |

## 8. 권한과 데이터 보호 계획

공개·비공개는 화면에서만 숨기는 기능으로 끝내지 않는다. 서버 또는 DB 접근 정책에서도 소유자와 공개 범위를 확인해야 한다. Supabase를 사용한다면 RLS 정책을 설계하고 다른 계정에서 비공개 글·보관함에 접근할 수 없는지 검증한다.

본문 편집기는 사용자 입력을 다루므로 스크립트 실행을 막는 검증과 안전한 렌더링이 필요하다. 사진은 파일 유형·크기·소유권을 확인하고, 비공개 글의 사진도 공개 주소로 노출되지 않도록 저장 정책을 정한다.

비밀 API 키, 서비스 관리자 키, 외부 연동용 사용자 토큰은 GitHub에 올리지 않는다. 유출되면 타인의 계정·데이터 접근이나 권한 남용으로 이어질 수 있고, 파일을 나중에 지워도 Git 기록에 남을 수 있기 때문이다. 환경 변수 예시에는 실제 비밀값 대신 항목 이름과 설명만 작성한다.

## 9. 단계별 개발 순서

1. **기획 확정**: 동기·목표·첫 버전 범위와 과제 마감일을 확인한다.
2. **기능명세서 작성**: 화면별 동작과 성공·실패 조건을 구체화한다.
3. **화면 설계**: 공개 포트폴리오, 탐색, 개인 관리, 작성 화면을 정한다.
4. **API 명세서·ERD 작성**: 요청·응답·권한·오류와 데이터 관계를 설계한다.
5. **개발 환경 구성**: 프레임워크, Git, 환경 변수, DB·인증 설정을 구성한다.
6. **핵심 기능 구현**: 로그인·프로필 → 작성·공개 범위 → 조회·검색 → 핀·보관 → 기록 연결 순으로 작게 구현하고 확인한다.
7. **검증과 무료 배포**: 두 계정 권한, 데이터 유지, 반응형, 실패 상태를 점검하고 Vercel에 배포한다.
8. **제출 정리**: 실제 동작에 맞춘 문서와 README, GitHub·배포·블로그 링크를 정리한다.

사용자와 한 단계씩 대화하며 결정한다. 이번 단계에서 구현이나 배포까지 진행하지 않는다. 상세 일정과 마감일은 확인 후 추가한다.

## 10. AI 사용과 검증 기록 방식

Codex를 기획 정리·설계·코드 작성·문서화에 사용하되, 사용자가 선택한 방향과 AI의 제안을 구분한다. 각 단계에 ‘AI가 제안한 내용 / 내가 선택·수정한 내용 / 실제 확인 방법과 결과’를 남긴다.

화면 캡처는 실제 구현 화면을 사용한다. 오류가 없었던 단계에는 오류를 만들지 않고, 미검증 기능은 완료했다고 표현하지 않는다. 커밋 수와 테스트 통과도 실제 결과만 기록한다.

# 백엔드 통합 점검

백엔드 기능별 구현을 마친 뒤 기능 간 상태 전환을 확인했다. 이후 탐색 피드·최소 상세와 공개 메타데이터를 추가 검증했다. 회원 작업 화면은 후속 단계에서 구현·검증했으며 `blog/15-member-workspace.md`에 별도로 기록했다. 개인 포트폴리오와 일부 관리 UI·Vercel 배포는 후속 범위다.

## 검증 결과

| 검사 | 환경 | 결과 |
|---|---|---|
| 전체 자동 테스트 | Node.js + API 응답 모의 + PGlite | 42개 통과, 실패·건너뜀 0개 |
| TypeScript 검사 | `npm run typecheck` | 통과 |
| 프로덕션 빌드 | `npm run build` | 통과 |
| Supabase 공개 조회 | 실제 서울 프로젝트, publishable key | 6개 테이블 조회 정상 |
| HTTP 상태·오류·캐시 정책 | 개발 서버 및 빌드 후 실행 서버 | 공개 조회 200, 입력 오류 400, 미인증 401, 없는 대상 404, `no-store` 확인 |
| 인증 필수 API | 두 실행 환경, 23개 메서드·경로 조합 | 토큰 없이 모두 401, 데이터 변경 없음 |
| 개발 검증 화면 | 프로덕션 `/auth/check` | 404 |

테이블 조회가 200이라는 사실만으로 모든 RLS 규칙을 증명하지 않는다. 소유자·다른 회원·방문자의 권한과 상태 전환은 실제 마이그레이션을 적용한 PGlite 테스트로 검사한다. 이전 기능별 실제 OAuth·사진 업로드 검증은 `docs/blog/05-*`부터 `12-*` 자료에 기록했다. 이번 실연결 검사는 읽기와 인증 거부만 확인하며, 로그인한 회원의 모든 변경 요청을 호스팅 DB에서 재실행한 것은 아니다.

## 기능 간 통합 시나리오

`tests/backend-flow.test.ts`는 마이그레이션 8개를 순서대로 적용하고 다음 흐름을 검사한다. 추가한 feed_metadata의 회원 보관 여부·익명 격리·비공개 제외·20개 입력 한도도 함께 검사한다.

1. 작성자가 프로젝트·공부 기록을 생성하고 사진을 첨부해 공개한다.
2. 두 기록을 연결하고 프로젝트를 핀으로 지정한다. 다른 회원이 공개 기록을 보관한다.
3. 작성자가 제목·본문·사진을 수정해도 공개 검색·핀·연결 목록과 발행 사진은 이전 발행본을 유지한다.
4. 오래된 초안 버전으로 발행하면 거부한다. 첨부 해제만으로 기존 발행 사진을 제거하지 않는다.
5. 비공개 적용 후 방문자와 다른 회원에게 기록·사진·연결이 숨겨진다. 핀은 제거하고 보관 참조는 유지한다.
6. 휴지통 이동 후 편집·발행 접근을 차단한다. 복원은 비공개이며 연결 참조를 유지한다.
7. 다시 공개하면 다른 회원의 보관함과 공개 연결에서 새 발행본을 볼 수 있다. 핀은 직접 다시 지정한다.
8. 오래된 발행 버전의 변경을 거부하고, 참조가 사라진 사진만 정리한다.

Storage 테스트는 객체 메타데이터와 SQL 정책을 검사한다. 이미지 바이트 디코딩·변환과 API 처리는 `tests/images.test.ts`에서 별도로 검사한다. PGlite는 Supabase Auth·PostgREST·Storage HTTP 서버를 실행하지 않는다.

## 프런트엔드 연결 규칙

- 초안은 작성 중 내용, 발행본은 마지막 정식 저장 내용이다. 수정 후 명시적으로 적용해야 공개본이 바뀐다.
- 수정·사진 작업·삭제·복원 후 응답의 최신 버전을 사용한다. 409 충돌에서는 먼저 최신 내용을 조회하고 덮어쓰기를 안내한다.
- API의 인증 토큰은 Supabase access token이다. 로그인·갱신·로그아웃 상태에 맞춰 요청한다.
- 사진 원본은 예약 후 Storage에 직접 업로드한다. 완료 API 성공 후 반환된 초안 버전으로 본문 저장과 발행을 진행한다.
- 비공개 사진은 인증된 요청으로 받은 Blob을 표시한다. 토큰을 URL에 넣지 않는다.
- `image_cleanup_pending`이 참이면 저장 성공과 파일 정리 재시도를 구분한다.
- 본문 렌더링은 사용자 콘텐츠를 안전하게 처리해야 한다. 최종 편집기·자동 저장·반응형 화면·로딩 및 실패 안내는 프런트엔드 단계에서 구현한다.

## 재현 명령

```powershell
npm test
npm run typecheck
npm run build
# 개발 서버 실행 중
npm run check:connection
# 별도 터미널에서 프로덕션 서버 실행
npm start -- --port 3100
# 프로덕션 서버 실행 중
npm run check:connection -- http://localhost:3100
```

연결 스크립트에는 사용자 토큰이나 서버 키가 필요하지 않다. `.env`의 프로젝트 URL과 publishable key를 사용하며 응답의 개인 데이터·설정 값은 출력하지 않는다.

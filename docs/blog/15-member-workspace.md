# 내 아카이브·프로필·기록 작성기 구현

탐색 화면에 이어 회원이 직접 기록을 남기는 화면을 연결했다. 흰 배경과 얇은 테두리를 유지하면서 내 아카이브, 프로필 설정, 항목 안내와 자유 본문을 함께 사용하는 작성기를 구성했다. 이번 단계는 기존 백엔드를 재사용하며 DB 구조와 API 이름을 변경하지 않았다. 티스토리에는 아직 게시하지 않고 설명과 실제 캡처를 준비했다.

## 입력에서 저장·화면까지

1. `ExploreShell`이 Supabase 브라우저 클라이언트의 세션을 확인한다. `MemberGate`가 로그인과 프로필 등록 상태를 검사한다.
2. 프로필은 `/api/me`에서 읽고 신규 회원은 POST, 기존 회원은 PATCH로 저장한다. 서버의 입력 검증 함수를 화면에서도 재사용한다.
3. 작성기는 기존 초안과 발행본을 각각 조회한다. 초안 버전과 발행본 버전은 별도로 보관한다. 발행본이 없는 신규 기록은 발행 버전 0이다.
4. 입력이 10초 멈추면 현재 내용의 사본을 저장 큐에 전달한다. 최초 저장은 POST, 이후 저장은 최신 버전을 포함한 PUT이다. 같은 내용을 중복 저장하지 않고 요청을 직렬 처리한다.
5. 저장 요청 중 사용자가 입력한 새 내용은 응답으로 덮어쓰지 않는다. 첫 저장 뒤 URL에 초안 ID를 넣으므로 새로고침하면 서버에 저장된 초안을 다시 읽는다.
6. 발행 버튼은 초안 저장 완료 후 두 버전과 공개 범위를 발행 API에 전달한다. 초안 자동 저장은 공개 본문이나 공개 범위를 변경하지 않는다.
7. 사진은 예약 후 사용자 인증으로 비공개 Storage에 직접 업로드한다. 서버에서 실제 이미지 검증을 마친 뒤 서비스 사진 URL을 본문에 삽입한다. 비공개 미리보기는 인증 헤더를 포함한 Blob 요청으로 표시한다.
8. 아카이브는 본인 기록만 조회한다. 휴지통과 복원은 초안·발행 버전을 전달하고, 오래된 버전이면 다시 조회하도록 안내한다. 복원은 비공개 상태다.

## 실패와 입력 보호

- 409 충돌은 입력을 유지하고 저장을 중단한다. JSON 백업과 명시적인 서버 재조회 버튼을 제공한다. 서버 재조회는 현재 입력을 교체하므로 확인창을 거친다.
- 최초 POST 응답이 유실되면 서버 생성 여부를 알 수 없다. 같은 내용을 자동으로 다시 POST하지 않고 아카이브에서 서버 초안을 확인하도록 한다.
- 기존 PUT 실패는 버전과 저장 성공 상태를 갱신하지 않는다. 서버가 이미 저장했다면 재시도에서 버전 충돌로 감지한다.
- 저장하지 못한 입력은 새로고침 후 복원을 보장하지 않는다. 탭 종료와 화면의 이동 링크에는 저장되지 않은 변경을 알리는 확인 처리를 제공한다.
- 계정이 바뀌면 회원 화면을 새로 구성하고, 요청 직전에 현재 세션의 사용자 ID를 다시 검사한다.
- 원본 업로드·검증·사진 정리는 각각 실패할 수 있다. 예약 취소, 완료 재시도, 원본/분리 사진 정리 재시도를 제공한다. 일부 정리 실패를 성공으로 숨기지 않는다.
- Markdown에 포함된 임의 HTML은 실행하지 않는다. `javascript:` 링크와 외부 사진도 표시하지 않는다. 수식의 신뢰 옵션은 비활성화한다.

|---|---|
| 자동 저장 | 실제 회원으로 제목·태그·본문 입력 후 약 10초 뒤 저장 완료와 초안 ID URL 확인 |
| 새로고침 복원 | 실제 초안의 제목·태그·본문 재조회 확인 |

| 프로필 수정 | 기존 값 그대로 PATCH 저장 성공 확인, 개인 정보 변경 없음 |
| 사진 | 생성한 PNG를 직접 업로드·검증 완료·본문 삽입·비공개 Blob 미리보기 확인 |
| 발행 | 검증용 기록을 공개 발행해 상세의 코드·수식·사진을 확인한 뒤 비공개로 전환 |
| 동시 편집 | 두 화면에서 같은 초안 조회 후 첫 화면 저장, 두 번째 화면 409와 입력 유지 확인 |
| 아카이브 | 실제 본인 기록·검색·상태 필터, 오래된 발행 버전의 삭제 거부·재조회 확인 |
| 휴지통·복원 | 검증용 기록 이동, 휴지통 조회, 비공개 복원 확인 |

| 비공개 접근 | 개발·프로덕션에서 토큰 없는 회원 API 401, 비공개 기록·사진 404 확인 |
| 프로덕션 화면 | 빌드 실행 서버의 `/write`에서 미로그인 안내 확인 |
| 자동 검사 | 기존 37개와 새 작성기 검사 5개, 총 42개 통과. 타입 검사·프로덕션 빌드 통과 |

실제 다른 계정 전환, 신규 프로필 등록, 대량 아카이브 추가 조회, 사진 정리 서버 장애와 GitHub 가져오기 UI의 성공 요청을 이번 단계에서 모두 재현한 것은 아니다. 계정 변경 차단은 모의 세션 테스트, API 입력/권한/페이지/사진 실패는 기존 API·PGlite 테스트로 검증했다. GitHub 가져오기의 실제 성공은 이전 11단계 자료에 기록했다.

## 발견한 오류와 해결

- 새 저장 큐 테스트가 Node의 TypeScript strip-only 실행에서 생성자 parameter property를 지원하지 않아 실패했다. 일반 필드 선언과 생성자 할당으로 바꿔 기존 테스트 실행 방식을 유지했다.
- 충돌 시 입력 영역까지 숨기는 첫 구현은 입력을 확인하기 어려웠다. 입력 영역은 그대로 표시하고 수정·저장만 비활성화하도록 바꿨다.
- 수식 렌더러와 직접 설치한 KaTeX CSS 버전이 달라 중복 의존성이 생겼다. 렌더러가 사용하는 0.16.47로 맞춰 CSS와 렌더링 버전을 통일했다.
- 최종 재빌드 때 OneDrive 동기화 폴더의 기존 `.next/server/app/archive`가 ReparsePoint로 표시되어 Next가 폴더를 unlink하려다 EPERM을 반환했다. 실행 서버를 중지하고 기존 `.next`를 Git에서 제외된 `node_modules/.cache/next-build-backup-*`에 보관한 뒤 새 빌드를 실행해 통과했다. 소스와 데이터베이스는 변경하지 않았다.
- 공개 범위를 다른 화면에서 바꾼 뒤 오래된 아카이브 목록에서 삭제하면 버전 충돌이 발생했다. 정상적인 보호 동작이며 오류를 표시한 뒤 목록을 다시 조회하여 처리했다.
